# Image Generation (Generate → Images)

Production image generation via OpenRouter’s dedicated **Images API**, integrated into AI Film Studio’s Generate menu.

## User entry points

| Path | Role |
|------|------|
| `/tools/image-generation` | Generate → **Images** workspace |
| Generate nav | Images, Video, Fix Shot, Music, Voiceover, Character |
| Tools index | Image generation card |

Optional query: `?projectId=` or `?project=` to associate generations with a project.

## OpenRouter endpoints

| Purpose | URL |
|---------|-----|
| Model discovery | `GET https://openrouter.ai/api/v1/images/models` |
| Generate | `POST https://openrouter.ai/api/v1/images` |

All calls are **server-side** using `OPENROUTER_API_KEY` / `NUXT_OPENROUTER_API_KEY`.

The older Character Creator / storyboard path still uses chat completions (`/api/generate/image` + `openRouterGenerateImage`). Generate → Images uses the dedicated Images API (`/api/generate/images`).

## App API routes

| Method | Route | Role |
|--------|-------|------|
| `GET` | `/api/openrouter/image-models` | Normalized live catalog (+ cache) |
| `POST` | `/api/generate/images` | Generate, stage, persist |
| `GET` | `/api/generate/images` | History (auth) |
| `GET` | `/api/generate/images/:id` | Detail |
| `DELETE` | `/api/generate/images/:id` | Delete |
| `GET` | `/api/generate/images/media/:id/:index` | Serve image (Bearer or `access_token`) |

## Model discovery & caching

1. Server fetches OpenRouter `/api/v1/images/models`.
2. Rows are normalized by `lib/normalize-image-model.ts` into `ImageModel` (capabilities, pricing, badges).
3. In-memory cache ~**45 minutes**. On refresh failure, **stale cache** is served; if empty, a small fallback list is used.
4. Default model: `OPENROUTER_DEFAULT_IMAGE_MODEL` or `DEFAULT_IMAGE_MODEL` in `lib/image-generation-defaults.ts`, with graceful fallbacks.

Badges (`FAST`, `QUALITY`, `EDITING`, `REFERENCE IMAGE`, `LOW COST`) come only from metadata or explicit overrides — never invented.

Unsupported parameters are **never** sent: `buildOpenRouterImageRequest` filters by `supportedParameterKeys`.

## Storage

1. Generated bytes are staged under `.data/image-generations/<stageId>/`.
2. Served at `/api/generate/images/media/<stageId>/<index>`.
3. PocketBase collection **`image_generations`** stores prompt, final_prompt, model, status, settings, film_controls, cost, and `output_images` files.
4. When a project is selected, images are also saved to **`project_assets`** with `metadata.source = 'image_generation'` and a generation id linkage (no duplicate reuse required later — reference the asset id).

Run schema setup:

```bash
npm run setup-db
# or for existing DBs:
npm run add-fields
```

## Prompt + film controls

User prompt is stored as `prompt`. Film controls (shot, angle, lens, lighting, style) are merged into `final_prompt` via `lib/image-generation-prompt.ts` without replacing the user’s text.

## Credits / usage

There is **no in-app credit ledger** yet. OpenRouter cost is stored when returned (`usage` / `cost`). Configure future app pricing in `lib/image-generation-credits.ts` (`resolveImageGenerationUsageCharge`) — never trust client-supplied credit values.

## Future: Storyboard & Video

### Storyboard → Images (implemented)

From a board panel, **Images…** opens `/tools/image-generation` with:

- `projectId`, `sceneId`, `shotId`, `frameRole`
- Stashed prompt (`imagePrompt` / description) + film controls derived from `shotType` / `cameraMove`
- `returnTo` back to the project storyboard

On generate, the server replaces the existing storyboard frame asset for that shot/role and writes a new `project_assets` row (`kind: storyboard`) with `metadata.shot_id` / `frame_role`.

Helpers: `lib/image-generation-prefill.ts`, `lib/shot-to-film-controls.ts`.

### Images → Video (implemented)

**Use as Video Start Frame** stashes a `VideoGenerationPrefill` with `startFrameUrl = projectAssetMediaPath(projectId, assetId)` and opens `/tools/video-generation`. Staging still runs via `ensureVideoStartFrameUrl` at generate time.

Keep the generator as a reusable workflow (composable + page) rather than a one-off screen.
